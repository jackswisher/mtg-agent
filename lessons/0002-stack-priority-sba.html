Lesson 02 · mtg-agent

Where this engine stops being Magic

You know the rules. The engine knows most of them. The gap is where your agent will learn things that aren't true.

An agent trained against a rules engine learns that engine, not Magic. Every divergence is a false lesson baked into the policy. Before you spend GPU hours, you need to know which ones are here.

Three below, each verified by running the code. Start with the good news.

1. The stack and priority are right

pass_priority (rules.py:3905) is a faithful implementation:

state.passed_priority[state.priority_player] = True

if state.both_players_passed():
    if state.stack:
        state = self.resolve_top_of_stack(state)   # ONE object
        state.reset_priority()                     # then priority resets
    else:
        state = self.advance_phase(state)
else:
    state.switch_priority()

One object resolves, then both players get priority again — CR 117.3b/608. Not "resolve the whole stack," which is the usual shortcut in toy engines. Counterspells genuinely work; responses genuinely work.

The eight priority windows in PRIORITY_PHASES match real Magic, with two small omissions: no priority in the combat damage step, and no end-of-combat step. Neither will hurt you soon.

Why this matters for the mission

The hard part of a Magic engine — the stack — is the part this repo got right. That's a meaningful argument for building on it rather than replacing it. Hold that thought until lesson 4.

2. There are two damage systems, and they don't talk

Combat damage lives in a local dictionary, created fresh inside _execute_combat_damage and thrown away when combat ends (rules.py:1389):

damage_marked: dict[int, int] = {}   # card_id -> damage taken

Spell damage lives somewhere else entirely — an attribute on the card (rules.py:3463):

target_creature.damage_marked = getattr(target_creature, "damage_marked", 0) + card.deals_damage

Same name. Different objects. Neither one ever reads the other. Nor does _get_effective_power_toughness consult either.

The consequence, which you can run:

uv run python -c "

Shock the 2/2, then attack it with a 1/1. One plus one is two, which is lethal on a two-toughness creature. It lives.

3. Damage never wears off

CR 514.2: damage is removed from all permanents during each cleanup step. The cleanup code has a comment saying it does this:

# Clear damage and temporary effects (Prowess, pump spells)

It clears the temporary effects. It does not clear the damage.

c.damage_marked = 1
for i in range(3):
    st = eng._execute_cleanup(st)
# damage_marked after 3 cleanup steps: 1

So a creature Shocked on turn 3 is still carrying that point on turn 9. Combine with divergence 2 and you get an engine where creatures are permanently fragile to spells and completely amnesiac about combat — opposite errors in the two systems.

What your agent learns from this

That chip damage from burn is a durable investment (it isn't) and that chip damage in combat is worthless (it isn't). Both distortions push a policy toward burn-to-the-face and away from combat math — on a benchmark whose flagship archetype is Mono-Red Aggro.

4. State-based actions run in one place

CR 704.3: SBAs are checked whenever a player would receive priority. Here, _check_state_based_actions has exactly one call site — inside combat damage:

grep -n "_check_state_based_actions" mtg/env/rules.py
# 1440:  state = self._check_state_based_actions(state, deaths)   <- the only call
# 1791:  def _check_state_based_actions(

Outside combat, lethal conditions are caught by ad-hoc inline checks at each call site instead — which is why a Shock that kills still works (rules.py:3467 checks lethal right there). It functions, but every new card effect has to remember to re-implement the check. That's the maintenance tax you'd inherit when scaling the card pool.

The docstring also advertises five checks:

Claimed in docstringActually implemented
Creatures with 0 or less toughness dieYes
Players at 0 or less life loseYes
Creatures with lethal damage dieNo
+1/+1 and −1/−1 counters cancelNo
Auras attached to nothing dieNo

Read the body, not the docstring. That holds generally in this file.

Check yourself

Q1You Shock a 3/3, then block it with a 2/2 the same turn. In this engine, what happens to the 3/3?

Survives. Spell damage sits on card.damage_marked; combat damage sits in a local dict inside _execute_combat_damage. Neither reads the other, so the engine sees 2 combat damage on a 3-toughness creature and calls it fine.

Q2Which behaviour did this engine get right relative to the Comprehensive Rules?

The stack. pass_priority resolves a single object and calls reset_priority(), exactly as CR 117.3b requires. The other three are the divergences from this lesson.

Recall. Without scrolling: name the two places damage is stored in this engine, and say why storing it twice is the bug rather than a detail.

A local damage_marked dict inside _execute_combat_damage (discarded when combat ends), and a damage_marked attribute on Card written by spell resolution (never cleared).

Two sources of truth for one game concept. Lethal is a question about total damage, so any split representation answers it wrong unless every call site remembers to sum both — and none do. The fix is one persistent field on Card, cleared at cleanup, read by a real SBA check.
